# Day 8 프로젝트 체크포인트

프로젝트: 스마일게이트 한국어 혐오표현 탐지 서비스
모델: smilegate-ai/kor_unsmile (BERT 기반, 라벨 10개짜리 멀티라벨 분류)
스택: FastAPI + Streamlit + transformers + Docker
배포 주소: https://huggingface.co/spaces/oiehnow/swear


## 1. 실행 내역

### 1-1. 서버 실행 / Swagger
(캡처: http://localhost:8000/docs)
serve_in_thread로 서버 켜면 모델이 한 번 로드되고, /docs 들어가서 POST /predict 눌러보니
잘 돌아갔다.

### 1-2. 정상 문장
"오늘 날씨가 정말 좋네요" 넣어봤더니 clean 으로 나옴. 초록색으로 정상이라고 떠서 안심.

### 1-3. 혐오 문장
"너 진짜 못생겼다 꺼져" 넣으니까 악플/욕설이 제일 높게 나왔다. 밑에 10개 카테고리 점수가
막대그래프로 같이 뜨는데 이게 좀 보기 좋더라.

### 1-4. 인증 / 입력 검증
(캡처: 테스트 셀 출력)
- 키 안 넣고 요청 → 401
- 빈 칸 보내면 → 422
- 제대로 보내면 → 200
이렇게 세 개 다 확인함.

### 1-5. 배포
(캡처: HF Spaces Running 화면)
도커로 FastAPI랑 Streamlit 두 개 한 컨테이너에 묶어서 허깅페이스 Spaces에 올렸다.


## 2. 체크포인트 답변

### Q1. Pydantic 검증은 어떤 잘못된 입력을 막아주나?
text 필드에 min_length=1, max_length=1000 걸어놨다. 그래서
- 빈 문자열
- 1000자 넘는 너무 긴 글
- text가 아예 없거나 숫자 같은 엉뚱한 타입
이런 건 모델까지 가지도 못하고 422로 막힌다. 모델 돌리기 전에 거르니까 깔끔함.

### Q2. Depends(verify_api_key) 빼면 뭐가 위험한가?
한마디로 아무나 다 쓸 수 있게 된다. 키 검사가 없으니까 외부에서 막 요청 날려도 막을 방법이
없고, 그러다 서버 자원(특히 모델 추론) 다 잡아먹힐 수 있다. 허락받은 사람만 쓰게 하는
장치가 통째로 사라지는 거라 위험하다.

### Q3. run_in_executor 왜 썼나?
모델 추론이 시간 좀 걸리는 작업이라서. 이걸 그냥 돌리면 추론 끝날 때까지 서버가 다른 요청을
아예 못 받고 멈춰버린다. 그래서 추론만 따로 스레드로 빼서 돌렸다. 그러면 한 명 요청 처리하는
동안에도 다른 요청을 받을 수 있다.

### Q4. Day 1~8 중에 제일 많이 본 Day는?
Day 6, 7. auth.py(인증)는 Day 6 거 거의 그대로 가져다 썼고, 서버 시작할 때 모델 한 번 로드하고
run_in_executor로 추론 돌리는 구조는 Day 7에서 한 거랑 거의 똑같았다. 허깅페이스 모델 가져다가
FastAPI로 감싸는 흐름 자체가 Day 7이랑 제일 비슷했음.

### Q5. 실제로 배포하려면 뭐가 더 필요한가?
- 코드에 박아둔 API 키를 환경변수나 시크릿으로 빼야 함 (지금은 그냥 박혀 있음)
- 의존성 고정해서 어디서든 똑같이 돌게 하기 → 이건 도커로 이번에 함
- 로그랑 모니터링 (요청 얼마나 오는지, 에러 얼마나 나는지)
- 사람 많이 몰리면 GPU 서버 쓰거나 모델 가볍게 만들기
- HTTPS, 죽으면 자동 재시작 같은 안정성 처리
일단 도커 + 허깅페이스로 배포는 한 번 해봤다.


## 3. 회고

### 잘된 거
빈 노트북 받아서 스키마, 모델 서비스, 서버, 화면까지 직접 다 채우고 배포까지 한 게 뿌듯하다.
평가 기준(서버 실행, Swagger, 401, 422, Streamlit) 다섯 개 다 통과했고, 필수 아닌 배포까지
해봐서 좋았다.

### 힘들었던 거
- transformers 버전이 최신이라 그런지 토크나이저 출력 형식이 바뀌어서 추론이 자꾸 에러났다.
  옵션 하나 바꿔서 겨우 해결. 이 모델이 멀티라벨이라 sigmoid를 써야 한다는 것도 이때 알았다.
- 제일 황당했던 건 포트 충돌. 전에 켜둔 Day 7 서버가 8000번을 잡고 있어서, 내 서버 안 뜨고
  엉뚱한 서버로 요청이 가서 KeyError가 났었다. /health 찍어보고 모델 이름 보고 나서야
  "아 이거 옛날 서버구나" 하고 알아챘다. 헬스체크가 왜 중요한지 이때 확실히 느낌.

### 배운 거
내 컴퓨터에서 돌아가는 코드랑, 남이 진짜 쓸 수 있는 서비스는 완전히 다른 거였다.
인증, 검증, 비동기, 배포 이런 게 그 차이를 만드는 거였고. 모델 자체보다 모델을 잘 감싸서
안 죽게 서빙하는 쪽이 더 일이 많다는 걸 알았다.

### 다음에 할 거
API 키 시크릿으로 빼는 거랑 로그/모니터링 붙여보기. 도커 더 익숙해지면 자동 배포(CI/CD)도
공부해보고 싶다.
